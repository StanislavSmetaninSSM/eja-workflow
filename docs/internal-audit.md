# Internal completion audit

Local experimental candidate0.10.2 tests a native internal loop for Kimi Work on Windows. Live acceptance is pending; safe private main0.9.1 remains the fallback. Only Stop and exact-auditor PreToolUse are declared; UserPromptSubmit/sessionStart/systemPrompt contributions and project AGENTS initialization are absent. It never calls `conversations.send`, types into the user input, changes permission/auto mode, starts a service or patches the application. Native Stop appends internal role:user context with system_trigger origin; the projector filters that origin from displayed user messages. Rendered-UI acceptance of this candidate remains pending. No native plugin preferences panel was found, so an external chat-report option is not shipped.

The native Stop hook can request **one continuation per turn**, in the exact invoking agent. Its `stop_hook` origin is filtered from displayed user messages. Normal assistant continuation and tool activity may still be visible; the first final-looking answer may already have streamed. This is not a promise of invisible processing.

1. When persisted session evidence suggests active engineering work, Stop issues a random local ticket and asks the invoking agent to run one exact auditor command. Ordinary factual conversation and questions awaiting user decisions are exempt. This eligibility signal can miss unflushed or unsupported work; no coverage is inferred from silence. Current eligibility can miss documentation-only writes and read-only tasks without qualifying Bash/Agent/skill calls.
2. A narrow PreToolUse hook recognizes only this plugin's fixed audit command and records the native `session_id` and `tool_call_id`. It allows other commands unchanged. Invalid/duplicate fixed invocations are refused; unsupported wrappers get no new binding and cannot establish a verified report through that wrapper. Source reads/searches/hashes remain unchanged. This is not a general shell parser or write-tool broker.
3. The actual audit tool waits up to four seconds for exactly that call id and command in the exact session's supported agent journals. It also requires this ticket's exact native `system_trigger/stop_hook` message in that caller's same open kernel task. Actor runs may end and restart inside it; kernel turn.prompt/turn.ended and canonical numeric/decimal-string ids define the boundary. Recheck must retain that boundary; a new user turn or in-turn steering invalidates it. Absent, stale, ambiguous or unsupported evidence is refused. It does not select the latest file or infer caller identity from the shared Stop session id.
4. Its redacted JSON is the ordinary tool result, routed by Kimi to the exact caller. The agent is instructed to repair applicable omissions within the original task contract and run the returned `next_action` once. The ticket permits one check and one recheck, without repeated internal prompts.

This runs **before native turn completion**. Reports say `boundary: pre_completion_tool`, `task_completion: PENDING` and `workflow_status: NOT_PROVEN`. The checker excludes only its own pending tool call; any other unmatched call or unknown record remains UNVERIFIED. A checkpoint PASS is not a completed-task or full-methodology PASS.

The checkpoint checks successful entry/order, using-superpowers and verification. Retained successful skill loads may establish availability; they do not establish current-task verification. Current-task successful implementation/execution skill evidence establishes observed implementation intent: code/test writes then require execution/TDD availability before the first such write. Code writes alone can be review probes; without that role evidence the report retains code_write_role_applicability UNVERIFIED, blocks formal recovery/PASS, and does not demand implementation phases from a reviewer. Both paths require a new successful shell check after the last observed code write. Role meaning remains manual. Main callers with current native Agent results also receive scoped child profile/entry/verification checks. Read-only child review does not require implementation/planning again. Full native Spec Kit artifacts/phases, actual RED/GREEN, approval and scope semantics, real test meaning, arbitrary shell effects and independent-review meaning still need independent review. The standalone auditor has a separate, explicit-role contract.

Original reports are created exclusively and never rewritten by recheck. `FORMAL_RECOVERED_LATE` requires relevant actual successful Skill calls and a new observed successful shell check, with no unresolved finding; suggestive arguments on another tool do not count. It does not establish that the command was a meaningful test or erase an earlier order violation. Unresolved/unknown evidence stays explicit. Do not regenerate history, fabricate RED/approval or reimplement a correct product to satisfy an ordering check.

Runtime metadata is under `KIMI_CODE_HOME/eja-workflow-audit/tickets/`, outside source and journals. It contains ticket/binding ids, paths, times and redacted reports, not user prompts, titles, reasoning, private profiles or raw tool outputs. It is not committed or uploaded. Python3.10+ with the standard library is required; the command uses `python` from Kimi's PATH. Missing runtime, hook timeout or model refusal can leave an issued ticket unused. Unused does not mean PASS.

Disabling the plugin excludes its hooks through the native engine. There is no background delivery process to keep sending. A model can still ignore the internal instruction or its tool report; the platform's one-continuation limit prevents the plugin from forcing another pass. Actual ordinary-task evidence is required before claiming any measured improvement. The original six-clean-task acceptance criterion remains unchanged.

A missing Skill may be loaded during correction without changing the original user task. Native model-tool Skill activation itself creates steering events. The guard accepts only a complete, uniquely correlated same-agent/current-prompt/current-kernel prompt.steered → skill_activation context message → turn.steer triple with matching singleton message ids, model-tool/inTurn origin and unique activation id. A matching successful Skill call/result with exact tool-call and parent UUID is required as corroboration; there is no native activation-to-tool-call foreign key. User/user-slash, combined, incomplete, duplicate, mismatched or ambiguous steering remains UNVERIFIED. Payload bodies are not retained in this correlation.
