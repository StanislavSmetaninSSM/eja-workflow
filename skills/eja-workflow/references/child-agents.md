# Дочерние агенты Kimi Work

Читай перед делегированием или работой дочернего агента. Родитель владеет требованиями, планом, интеграцией и приёмкой; ребёнок получает один ограниченный блок или независимое ревью. Применяй этапы методологии по роли, сохраняя одну каноническую feature.

`eja-methodology` — выбор по умолчанию для делегированной разработки, исследования и ревью, включая одну функцию. Профиль переносит правила методологии в отдельный контекст; загруженные родителем скиллы туда автоматически не переходят. Ребёнок выполняет только назначенную фазу и переиспользует согласованные артефакты, поэтому размер поручения не требует повторного полного планирования.

## Выбор и запуск

1. Проверь фактический каталог инструмента `Agent`. Этот плагин предоставляет профиль `eja-methodology` через `agents/eja-methodology.md`: его тело становится системным промптом выбранного дочернего агента. Поле `agents` в манифесте объявляет каталог. Это отдельный механизм от отключённой в проверенной Work версии основной инъекции `systemPromptPath`.
2. Для нового контекста укажи `subagent_type: "eja-methodology"`, короткое `description` и полный `prompt` с пакетом ниже. Если профиль не доступен, сообщи ограничение; реально имеющийся `coder` можно использовать с тем же явным пакетом, но не называй его нашим системным профилем. Не подменяй тип именем, которого нет в каталоге.
3. Для продолжения используй `Agent(resume: "agent-…", prompt: "следующий ограниченный шаг")` с фактически возвращённым agent_id; тип заново не задаётся. Контекст сохраняется. Новый независимый ревьюер вызывается без resume.
4. Выбирай модель только из поддерживаемых параметров и доступных вариантов. Отсутствие model в проверенном вызове не доказывает ручной выбор модели; не приписывай Kimi имена/уровни Codex. Проверяй фактический ответ инструмента: agent_id, actual_subagent_type, status и результат. Сообщение о запуске не равно завершению.

Поддерживаемая форма нового вызова:

```json
{
  "description": "Проверка сохранности согласованного контракта",
  "subagent_type": "eja-methodology",
  "prompt": "Роль: независимый ревьюер. Проверь переданный ниже пакет; результат — находки и доказательства, без реализации."
}
```

Это форма вызова, не готовый пакет. Перед отправкой дополни prompt всеми полями следующего раздела реальными данными текущей задачи. Имя профиля и поля сверяй с текущим Work: наличие определения на диске не доказывает его загрузку. При проверке установки отдельно подтверждай основной и дочерний системные контексты; текст, доставленный hook в user-контексте, не называй системной инъекцией.

## Пакет задачи

Передавай одним связанным пакетом:

| Поле | Содержимое |
|---|---|
| Роль и результат | Исполнение конкретных task ID, исследование с выводами или ревью указанного диапазона; что именно вернуть родителю |
| Исходный контракт | Оригинальный запрос и обязательные ограничения; не только пересказ исполнителя |
| Предложение и одобрение | Само предложение, на которое относится «всё подтверждаю», вместе с ответом пользователя. Если одобрён сразу точный запрос, укажи это. Пустая ссылка на согласие без утверждённого текста не устанавливает контракт |
| Канонические документы | Абсолютные существующие spec/plan/tasks, конституция и AGENTS; активная feature и текущие task ID. Не создавай конкурирующие документы |
| Состояние и проверка | Точная ревизия/diff либо проверяемые файлы, уже выполненные проверки и оставшиеся; команды и критерии результата |
| Границы | Абсолютный рабочий корень, разрешённые записи и scratch внутри него; запрет публикации/глобальных изменений, если они не разрешены |
| Методология роли | Явный старт для ребёнка, включая fallback `coder`: первым инструментом `eja-workflow:eja-workflow`, собственный `superpowers:using-superpowers`, bridge при совместном регулировании, затем применимые скиллы назначенной фазы. Абсолютные пути к этому справочнику и canonical contract-review.md. Для ревью передай полный текст последнего отдельным полем |
| Serena | Фактический сервер/проект, необходимые языки и проверенные символы, кто сейчас использует общий активный проект; готовность не выводится из YAML |

Если родитель сам выбрал техническую деталь, обозначь её как своё решение, а не пользовательское одобрение. Передавай неразрешённые вопросы явно. Массовая загрузка всех скиллов не заменяет подходящих фаз.

## Действия по роли

- **Исполнитель:** собственный вход, bridge для совместно регулируемой работы, чтение канонического контракта и выделенных tasks; execution, TDD для изменения поведения, debugging при дефекте, verification перед заявлением о готовности. Новое brainstorming запускает соответствующие Spec Kit фазы; готовое согласование повторно не запрашивается. Результат включает точный diff и доказательства.
- **Независимый ревьюер:** собственный вход и применимые правила ревью; проверка исходного согласования, кода/документов и исполняемые контрпримеры в разрешённом scratch. Планирование и реализация не повторяются ради отметки о вызове. Он не меняет контракт, не устраняет находки сам и не проверяет собственную реализацию как независимую.
- **Родитель после отчёта:** проверяет фактический diff/выводы, вызывает receiving-code-review, перечитывает полный contract-review.md и заполняет таблицу до решений. Только затем исправляет подтверждённые находки, выполняет проверки и закрывает tasks по доказательствам. Отчёт ребёнка не закрывает приёмку автоматически.

## Ограничения

Профиль сохраняет доступные родителю рабочие инструменты, кроме `Agent` и `AgentSwarm`, явно исключённых через `disallowedTools`; здесь не заявлена техническая изоляция файловой системы. В Work одного `subagents: []` недостаточно: основной агент исключает из доступных ролей профили, которым инструменты ещё позволяют делегирование. Поэтому исключены оба инструмента и оставлен пустой список дочерних ролей. Новое делегирование возвращается родителю. Не считай один запрет Write/Edit защитой, если остаётся Bash или другой путь изменения данных. Статический список инструментов не проверяет порядок этапов и полноту согласования.

Auto-режим — штатная особенность Kimi. Он может ограничивать инструмент уточнений и поощрять самостоятельные решения; не отключай и не исправляй его ради методологии. Отмечай реальную доступность вопросов и сохраняй исходные явные ограничения пользователя. Результат работы, соблюдение процесса и действовавший режим проверяются отдельно.
