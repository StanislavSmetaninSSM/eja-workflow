# Serena в Kimi Work: установка и проверка

Это рецепт для **Kimi Work**, не Kimi Code. Serena устанавливается отдельно; небольшой MCP-плагин Work подключается к её серверу. Eja Workflow не содержит сервер, языковые среды или постоянный установщик.

Новый маршрут проверен для **Serena 2.1.0, Python 3.13, Windows**, HTTP MCP, контекста `ide` и интерфейса `tools`. Результаты и границы проверки: [чистая установка](../../../docs/serena-clean-install.md). Работающие версии не обновляй или понижай ради совпадения с этим рецептом. Для иной версии сначала проверь её реальный help и доступные инструменты.

## 1. Сначала обнаружение

Проверь установленные плагины Work, реальный каталог MCP-инструментов, команду запуска/контекст/URL существующего подключения и его владельца. Если связь и символические запросы работают, сохрани установку. Не создавай второй сервер и не меняй активный проект другого клиента.

Ошибка `command not found` сама по себе не означает отсутствия пакета: у Work Bash и PowerShell различается PATH. Выполни `uv tool list --show-paths` и `uv tool dir --bin`, найди установленный `serena.exe`, проверь его по абсолютному пути. Не исправляй PATH переустановкой, глобальной сменой окружения или переходом на Git HEAD.

Отдельно проверь передачу manual. Контекст `agent` **исключает initial_instructions**, предполагая, что клиент уже передал полный текст. В Work это нельзя предполагать по имени контекста. Если полного текста нет и инструмент отсутствует, это `manual_unavailable`, даже при здоровом порте и доступном find_symbol. Чтение сырого Jinja/YAML-шаблона не заменяет rendered manual. Не вызывай отсутствующий инструмент снова и не запускай print-system-prompt как обход: он создаёт другой агент и может менять реестр/запускать LS. Существующий сервер сохраняется; изменение его контекста выполняется только в явно разрешённой настройке с учётом других клиентов.

## 2. Только новая отсутствующая установка

Установка должна входить в разрешённый пользователем объём. Сначала установи/найди [uv](https://docs.astral.sh/uv/getting-started/installation/), затем официальный пакет из PyPI. Проверенный свежий маршрут закреплён, чтобы подробный рецепт и установленный интерфейс совпадали:

```powershell
uv tool install -p 3.13 serena-agent==2.1.0
$serenaBin = (uv tool dir --bin).Trim()
$serenaExe = Join-Path $serenaBin 'serena.exe'
& $serenaExe --help
& $serenaExe init
& $serenaExe start-mcp-server --help
```

Выполняй команды последовательно и проверяй exit code/вывод каждой. `init` должен показать путь созданной конфигурации и backend LSP. Наличие пакета и успешный init ещё не означают работающий MCP или language server. Для уже существующей установки эти команды установки/инициализации автоматически не выполняются. Пин относится к проверенному новому маршруту, а не к запрету будущих версий: новую версию сначала проверяют тем же набором проб.

## 3. Предпосылки языков

Проверь только языки целевого исходного кода и окружение **того процесса**, который будет запускать сервер. Окружение другой консоли не доказывает доступность.

| Язык | Идентификатор | Требование |
|---|---|---|
| Python | python | Подходящий Python и доступные серверу uv/uvx для запуска адаптера; в свежей проверке — отдельный Python 3.13. Проверить реальный символ. |
| JavaScript/TypeScript | typescript | Node.js и npm доступны процессу сервера; на Windows проверить также npm.cmd. Адаптер отдельно получает language-server пакеты. |
| C# | csharp | .NET 10+ доступен процессу сервера. Проверить dotnet --info и нужный SDK/runtime. Не обещать автоматическую установку .NET самим адаптером. |

Добавь обнаруженные каталоги в PATH **процесса запуска**, при необходимости задай корректный DOTNET_ROOT. Не копируй чужой PATH и не меняй глобальное окружение. Установку отсутствующих Node/.NET выполняй отдельно в разрешённой области по официальному источнику. Ошибка загрузки LS или отсутствующий dotnet не исправляются переустановкой Serena.

## 4. Запуск нового HTTP-сервера

Выбери подтверждённо свободный loopback-порт; `9121` — пример, а не обязательный адрес. Занятый порт сначала сопоставь с владельцем. Чужой процесс не останавливай. Поддерживаемая команда для **новой 2.1.0**:

```text
<absolute-serena.exe> start-mcp-server --transport streamable-http --host 127.0.0.1 --port <free-port> --context ide --agent-interface tools --enable-web-dashboard false --open-web-dashboard false --enable-gui-log-window false --tool-timeout 120
```

Здесь `ide` сохраняет initial_instructions и убирает дублирующие файловые/shell-инструменты; `tools` даёт отдельные find_symbol/get_symbols_overview, которые использует Eja Workflow. В 2.1.0 нет значения `classic`. Не добавляй `--project`/`--project-from-cwd` при запуске общего сервера: контекст ide при заданном стартовом проекте включает single-project режим и может убрать activate_project. Проект активируется после получения manual и подготовки YAML.

Для фонового запуска Windows используй `Start-Process` с абсолютным FilePath, массивом ArgumentList, `-WindowStyle Hidden -PassThru`, отдельными файлами `-RedirectStandardOutput`/`-RedirectStandardError` в разрешённом каталоге и **без -Wait**. Сохрани PID, фактические аргументы и владельца. Проверь MCP после завершения запускающего PowerShell. Ожидание долгоживущего сервера foreground-командой агента может упереться в лимит команды. Постоянный автозапуск/восстановление после сбоя настраивается отдельно после успешной проверки, если это входит в запрос; запуск процесса не доказывает такой автозапуск.

## 5. Коннектор Work

Если коннектор отсутствует, прочитай установленный Work `plugin-builder/SKILL.md` и help его скриптов. Создай **новый** полный манифест генератором, подставив обнаруженные абсолютные пути и уже проверенный URL:

```text
python <plugin-builder>/scripts/create_plugin.py serena --type mcp --mcp-url http://127.0.0.1:<free-port>/mcp --path <new-source-parent> --display-name Serena --description "Semantic code tools through the local Serena MCP server" --locale en-US
python <plugin-builder>/scripts/validate_plugin.py <created-plugin-root>
python <plugin-builder>/scripts/register_personal.py <created-plugin-root>
```

Это шаблон: перед выполнением все значения должны стать реальными. Прочитай фактический путь из stdout генератора: в проверенном builder --path задаёт родительский каталог, к которому добавляются personal/serena. Последующие validate/register получают созданный каталог с kimi.plugin.json, а не автоматически исходное значение --path. Для русского запроса builder использует en-US, поскольку его locale-флаг поддерживает en-US/zh-CN; переведи вторую локализацию согласно его правилам. Не используй --force и не создавай конфликтующий id, если serena уже существует. Для существующего коннектора правится только зарегистрированный исходник с повышением версии; managed-копия не редактируется. Серверный пакет не копируется внутрь коннектора. В отдельной тестовой среде передай builder явный `--share-dir`, чтобы не затронуть действующий рынок.

После нулевых ошибок валидации и штатной регистрации установи через **Work → Плагины → Личные**; существующий плагин — **Обновить**. Регистрация не является установкой. Если UI недоступен, назови оставшееся действие. Новая сессия должна увидеть инструменты; не заявляй реальное нажатие без наблюдения.

## 6. Manual, проект, символы

1. Выполни реальный MCP initialize и проверь tools/list: initial_instructions, activate_project, get_current_config и нужные символические инструменты. Открытый TCP-порт или HTTP 200/405 на /mcp недостаточен.
2. Вызови initial_instructions, дождись успешного **полного rendered manual** и примени его. Прочитай реальные схемы tools/list: в проверенной 2.1.0 activate_project требует project и session. Возьми session текущего клиента из полученного manual, не выдумывай и не копируй идентификатор другого агента. Если инструмента нет/ошибка — останови этот путь настройки с точной причиной. Не заменяй успех шаблоном, именем контекста или доступностью других инструментов.
3. Прочитай существующие shared/local настройки проекта. Для нового проекта до первой активации используй полные шаблоны **установленной версии**, уникальный project_name и известные language_servers. Сначала shared project.yml, затем local. Не копируй ключи 1.7 вслепую в другую версию.
4. Список language_servers в local заменяет shared целиком: сохрани все явно выбранные языки/провайдеры и порядок, добавь необходимые python/typescript/csharp. Сохрани ignore-правила, workspace folders и backend. Пустой список не считается рабочей символикой. Активация незарегистрированного пути сохраняет запись проекта в serena_config.yml выбранного SERENA_HOME, даже когда оба проектных YAML уже существуют. Это запись вне каталога проекта; она должна входить в разрешённую настройку. Для тестов активируй только собственный сервер с собственным home; защищённый общий сервер не переключай.
5. Вызови activate_project по фактической схеме (в 2.1.0: project = абсолютный разрешённый корень, session = идентификатор из собственного manual), затем прочитай эффективную конфигурацию и выполни find_symbol с relative_path настоящего исходного файла каждого используемого языка. Успешная activate_project не доказывает готовность LS: инициализация может продолжаться, а первый get_current_config ждать её в очереди. Для первого config/symbol после такой активации действует бюджет запуска LS, а не обычного MCP-запроса. Проверь имя/тип/диапазон найденного символа, а не только транспортный успех. До появления исходника проверка ожидает; имя произвольного scaffold-скрипта не заменяет язык продукта.

## Ограничения времени и повторов

Для автоматической настройки задай таймауты вызывающих инструментов: discovery/help — 30 с, отдельная установка Python/пакета/предпосылки — 240 с, init — 90 с, готовность HTTP — 60 с, обычный MCP-запрос — 30 с, первый символический запрос/запуск LS — 120 с. Это **пределы попыток**, не обещание скорости сети. Общий бюджет автоматического ремонта — 15 минут; явный статус с причиной завершает исчерпанный бюджет.

На каждом этапе сохрани команду, exit code, длительность и короткую фактическую ошибку. Один целевой повтор разрешён после устранения найденной причины. Повтор той же постоянной ошибки, отсутствующий инструмент или неподдерживаемая версия завершают автоматический ремонт. При наблюдаемом прогрессе загрузки можно сообщить необходимость отдельного продолжения; молчаливый сброс таймеров запрещён.

Различай состояния: package/PATH → init → server → MCP → manual → project → LS/symbols. Укажи первый неуспешный переход, его практическое последствие и точное следующее действие. Не переустанавливай всю цепочку из-за одного отказавшего LS, не урезай исходники/ignore-правила и не разворачивай бесконечные исследования пакетов. Независимая разрешённая работа продолжается; обязательная проверка не объявляется выполненной и зависимая разработка по памяти не разрешается.

## Изолированный тест с нуля

Пустого SERENA_HOME и короткого PATH недостаточно для доказательства чистоты Windows-профиля. Для **каждого дочернего процесса теста** отдельно задай собственные HOME/USERPROFILE/APPDATA/LOCALAPPDATA, TEMP/TMP/XDG, UV_TOOL_DIR/UV_TOOL_BIN_DIR/UV_CACHE_DIR/UV_PYTHON_INSTALL_DIR/UV_PYTHON_BIN_DIR, Python/Node/.NET-кеши и нормальный Windows PATHEXT. Основное окружение пользователя не меняется.

Используй `UV_PYTHON_NO_REGISTRY=1` на всём тестовом дереве процессов: это отключает и обнаружение, и регистрацию Python через Windows. Явную загрузку выполняй `uv python install 3.13 --no-registry`; затем передай **проверенный абсолютный путь именно этого Python** в tool install и UV_PYTHON для сервера/uvx. Один `-p 3.13` может найти интерпретатор вне нового каталога. Перед тестом зафиксируй пустые каталоги; после — проверь pyvenv.cfg пакета и LS, настоящие пути процессов, отсутствие ссылок на другие профили и отсутствие тестовых регистраций. Не называй тест чистым при обнаруженной утечке окружения; сохрани отрицательный результат и исправь изоляцию.

Такой тест использует общий Windows OS/kernel и не равен отдельной чистой ОС. Получение символов проверяется отдельно от создания/валидации коннектора; фактическую установку в новом GUI Work не заявляй без неё.

## Подготовка проекта Serena1.7

Это заметки для сохранения существующих 1.7-установок, не свежий маршрут 2.1.0. В 1.7 отсутствие shared project.yml при наличии local могло приводить к его перезаписи пустым local-шаблоном; готовь shared до local/activate. Зарегистрированный проект мог держать конфигурацию в памяти: повторная activate, restart LS и переподключение к тому же серверу не гарантировали перечитывания YAML.

Если подтверждён такой кэш, не повторяй эти действия бесконечно. Перезапуск общего сервера, смена его контекста или снятие регистрации — отдельное разрешённое вмешательство с учётом других клиентов и уникальности проекта. Не удаляй чужие регистрации и не меняй рабочую 1.7 ради инструкции для нового ПК. При отсутствии безопасного обновления кэша оставь проверку открытой и сообщи конкретное ограничение. Для другой версии сначала установи её фактическое поведение.
