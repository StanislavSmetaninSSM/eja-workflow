# Kimi Work: адаптация моста и пользовательские правила

Это локальное дополнение к `spec-kit-superpowers-bridge`, а не копия или замена общего скилла. Текущий запрос пользователя и применимые инструкции проекта определяют разрешённый объём. Эти правила уточняют общие скиллы для Kimi Work.

## Доставка персонального протокола

В Windows плагин использует один штатный `UserPromptSubmit`: встроенный Windows PowerShell читает manifest, `hooks/prompt-intro.md` и `system-prompt.md` только из `KIMI_PLUGIN_ROOT`, возвращает UTF-8 JSON.message. Он не читает входящий stdin, не сохраняет данные запроса, не пишет файлы и не блокирует инструменты. Дополнительная установка Python/Node или обход ExecutionPolicy для него не нужен. Оболочка должна поддерживать Windows cmd и `%SystemRoot%`; иные ОС этим обработчиком не поддерживаются.

Это добавление текста к каждому пользовательскому запросу, включая продолжение и справочные вопросы; освобождение обычных вопросов от разработки сохраняется. Текст не является техническим запретом на пропуск фазы. Ошибка/тайм-аут оставляет запрос без добавленных правил, а catalog/Skill остаются доступным путём входа. Наличие manifest не доказывает доставки: проверяй публичный `hook.result` и маркер `eja-workflow delivery <версия>` до первого действия. Для дочернего агента и момента получения ревью повторная доставка не гарантирована; пакет ревью и контроль после отчёта остаются обязательны.

Если полный основной протокол уже присутствует в hook_result, не перечитывай его ради отчёта. Это не означает вызова entry/engineering скиллов. Откат доставки — удалить `hooks` через штатное обновление собственного плагина при отсутствии активных задач и проверить отсутствие маркера в новом запросе. Не меняй vendor-файлы и не выключай чужие плагины.

## Проект и Spec Kit в Kimi

Общий `spec-kit-superpowers-bridge` владеет методологией, системный промпт — условиями допуска. Здесь только адаптация среды.

- Установи корень разрешённого проекта до записи. Если пользователь ограничил все изменения одной подпапкой, scaffold, spec/plan/tasks и feature pin тоже остаются там. Обнаружение родительского `.git`/`.specify` не разрешает его изменять. Проверь фактические пути, возвращаемые штатными скриптами, до записи; при необходимости используй поддерживаемый явный путь/параметр внутри разрешённого проекта.
- Проверяй назначение самой операции, не только cwd: абсолютный путь, редирект, временный каталог и глобальный installer могут писать снаружи. Намеренные пробы размещай в `<разрешённый-корень>/.work/`. Обычные журналы, кэш и регистрация инструментов допустимы только в пределах действующих разрешений; при буквальном запрете любой внешней записи не скрывай эти побочные эффекты.
- Для продолжения прочитай feature pin, существующие specs и конституцию в разрешённом проекте; не выводи feature только из имени ветки.
- Если scaffold отсутствует, следуй [установке Spec Kit](dependencies.md#spec-kit): проверь `specify version`, текущую справку и разрешённый корень. Для нового проекта используй доступную интеграцию `kimi`; Codex для этого не требуется. Существующую интеграцию сохраняй. После настройки проверь реальную доступность `speckit-*` в Work; путь, созданный CLI, сам по себе не гарантирует обнаружение скиллов. Не применяй `--force` вслепую.
- Выполняй инструкции реальных speckit-фаз, включая применимые штатные скрипты и hooks. Имена файлов не доказывают выполнения. Если скилла нет в каталоге, прочитай установленный SKILL.md файловым инструментом и назови этот fallback честно; если нет и файла, укажи пробел.

## Superpowers и Kimi-инструменты

- `Skill`: точное имя из каталога. `TodoWrite` из переносимых инструкций соответствует доступному `TodoList`; файловые и shell-инструменты выбирай по реальной схеме.
- Для независимого агента используй доступный `Agent` с поддерживаемым типом, например `coder` для реализации/ревью, `explore` для чтения. Проверь текущую схему; не передавай вымышленный `general-purpose` или параметры моделей. Отсутствие Agent сообщи как ограничение независимого ревью.
- Пользователь по умолчанию предпочитает одного владельца целого блока и отдельного ревьюера. Делегируй реализацию только при конкретной пользе. Каждый пакет Agent содержит: исходные требования пользователя и неразрешённые решения; конституцию и spec/plan/tasks; точный diff/ревизии; сохраняемые контракты; разрешённые корни записи, запреты и scratch `<корень>/.work/review/`; команды и факты проверок. Ревьюер проверяет пропущенные требования и контрпримеры, а не только соответствие переписанному spec. Не предлагай `%TEMP%` или соседнюю папку без отдельного разрешения. Не позволяй параллельным агентам редактировать те же файлы.
- Модель текущего Kimi выбирает пользователь. Не утверждай переключение. Предпочтения пользователя для доступного выбора: реализация Sol 6.1 High (Medium для простого); обычное независимое ревью Sol 6.1 XHigh; сложное ревью Astra High. Это предпочтения, не названия обязательных Kimi-параметров. Если Kimi не предоставляет эти модели/настройки, прямо укажи ограничение и фактическую конфигурацию, если известна; используй отдельный доступный контекст, не выдавая его за указанную модель.
- Не прекращай Superpowers после создания spec: `test-driven-development` для поведения; `systematic-debugging` при сбое; `requesting-code-review`, при необходимости `receiving-code-review`, `verification-before-completion`; worktree discipline по проекту. Нет необходимости создавать новый worktree, если подходящий изолированный checkout уже есть.
- Независимое ревью обязательно и для документации/конфигурации: завершённый целый блок, свежий контекст, официальный шаблон Critical/Important/Minor, Strengths, вердикт готовности. Проверять исходные требования и реальные изменения, включая попытки воспроизвести дефекты. Исправь подтверждённые находки и запусти проверки. Повторное полное ревью — только при существенном изменении дизайна/валидности предыдущего; отдельное ревью каждого промежуточного документа не нужно. Перед разрешённым push adversarial-проверка должна быть покрыта этим ревью; само правило не разрешает push.
- Перед Agent добавь в пакет полный [протокол проверки контракта](contract-review.md). После отчёта прочитай его снова и запиши таблицу решений в существующие заметки tasks. Ревьюер не может согласовать изменение исходного требования за пользователя; его severity не заменяет твою проверку.

## Serena

Перед работой с кодом получи настоящий Serena manual и подготовь конфигурацию **до первой активации** по [проверенной последовательности](serena-work-plugin.md#подготовка-проекта-serena17). Затем `activate_project` и эффективная конфигурация. Для используемых C#, JS/TS, Python обеспечь соответственно `csharp`, `typescript`, `python`, сохрани другие явно настроенные языки/провайдеры и их порядок. Машинные уточнения — `.serena/project.local.yml`; этот файл не заменяет обязательный shared `project.yml`. Пустой список серверов не означает работающую символику.

Используй Serena для семантической навигации. Докажи доступ на реальном исходном файле каждого используемого в задаче языка через overview/find_symbol либо эквивалент. При старте отличай продолжающуюся инициализацию от записанной ошибки: читай traceback и текущую конфигурацию, не лечи постоянную ошибку бесконечным ожиданием. Сохраняй охват исходников и ignore-правила. Если сервер недоступен, сообщи причину и разрешённый fallback; не называй fallback успешной проверкой Serena.

В Serena1.7 зарегистрированный проект хранит конфигурацию в памяти: повторный `activate_project`, restart language server и переподключение клиента к тому же HTTP-процессу не гарантируют перечитывания файла. Если запрос перечисляет старые языки, зафиксируй кэш как причину и используй только подтверждённый доступный способ обновления из инструкции. Не переписывай shared config и не повторяй ожидания ради обхода кэша; не удаляй исходники или регистрацию посторонних проектов. Недоступность безопасного обновления — явное ограничение, не успешная настройка.

## C# XML-документация

Для каждого нового/изменённого API — точное описание контракта. `summary`, `param`, `typeparam`, `returns`: открывающий тег, текст, закрывающий тег на отдельных строках `///`. Все параметры с точными именами и значимыми null/empty/default-условиями; `paramref`, `see cref`, `see langword` по смыслу. Краткий `inheritdoc` допустим. Проверь новые XML-комментарии, включая test helpers, и сборку с XML documentation; не переформатируй посторонний код.
