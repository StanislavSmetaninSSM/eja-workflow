# Проверка исходного контракта при ревью

Отправитель читает этот файл перед ревью. Обязательный состав пакета Agent: исходные требования и источники одобрения; точный diff/ревизии; разрешённые корни и scratch. Полный текущий текст этого протокола включён в собственный профиль eja-methodology при сборке плагина. Для пакета прочитай соседний contract-review.ref.json и передай его объект без изменений как contract_review_ref; длинный текст вручную не копируется. Legacy-поле contract_review с полным текстом также поддерживается, но одновременно оба поля не передаются.

Ребёнок после входа/using читает этот файл целиком через Read по абсолютному пути до осмотра проверяемых файлов, команд и символических запросов. Наличие ссылки или текста в профиле не заменяет наблюдаемое чтение актуальной версии. Родитель снова читает файл после отчёта, до решений и закрытия задач.

## Авторитет требований

Исходный запрос и явно одобренные решения определяют контракт. Созданные агентом spec, Assumptions, research, тесты и отчёт ревью не создают нового согласия пользователя. Они могут содержать ошибки. Фраза «это явно записано в spec» не доказывает одобрение.

Для каждого нового обязательного критерия укажи исходное требование или конкретное одобрение пользователя. Выбранная агентом метрика без такого источника остаётся рекомендательной, включая числовые пороги производительности. Проверь допущения о допустимых входах, результате, гарантиях и ошибках. «Идиоматично» не является источником согласия.

## Таблица решений

Ревьюер заполняет таблицу для допущений и контрпримеров; исполнитель сверяет её с исходными требованиями и записывает итог в существующий `tasks.md` до закрытия задач:

| Исходное условие: точная цитата и источник согласия | Допущение / воспроизведённый контрпример | Вход: допустим / недопустим / не решено | Ожидаемый исход → фактический | Решение и доказательство / необходимое одобрение |
|---|---|---|---|---|

Классификация определяет проверку:

- **Допустим:** фактический результат выполняет все обещанные гарантии, включая тип. Если подкласс принят как допустимый, возвращённое им число не выполняет обещание строкового результата.
- **Недопустим:** фактически получена согласованная ошибка. При требовании `TypeError` произвольный результат не проходит проверку.
- **Не решено:** существенная трактовка допускает разные результаты; спроси только об этой разнице и оставь зависимую задачу открытой. Собственное Assumptions не определяет допустимость.

«Враждебный» или «патологический» не образуют четвёртую категорию. Для замечания без входных данных укажи «не применимо» и проверь непосредственно затронутое условие.

Итог каждой строки: **исправлено** (для поведения RED→GREEN; для документа — проверка исходного условия); **нужно решение пользователя** (задача открыта); **контракт не нарушен** (исходное условие и воспроизведение это подтверждают). Косметические замечания отделяй только если они не меняют ни одного условия контракта.

## Закрытие

Minor, редкость входа, YAGNI, зелёные тесты и неизменённый README не меняют контракт. Переклассифицируй находку по её эффекту; исключение требует конкретного решения пользователя.

Перед закрытием сопоставь таблицу, diff и свежие проверки с исходными условиями. Открытое нарушение или неутверждённая существенная трактовка запрещают полный успех. Продолжай независимую разрешённую работу; явно сообщи оставшийся вопрос/дефект. Заполненная таблица и мнение ревьюера не заменяют проверок.

## Исполняемые доказательства и правдивые задачи

Для каждого закрываемого task ID запиши в существующий tasks.md исходное условие/источник, фактический вызов или команду, результат и ограничение. Сверяй запись с настоящим stdout/результатом инструмента. Если исходные smoke-тесты прошли на заглушках, это успешная проверка экспортов; не называй её RED. Настоящий RED — наблюдавшееся нарушение нового поведенческого ожидания до исправления.

Проба с печатью значений подтверждает наблюдение, а её exit 0 — завершение процесса. Число напечатанных строк не равно числу пройденных проверок. Для утверждения «N/N пройдено» нужны assertions/явное сравнение с ожиданием и ненулевой exit при расхождении. Итог ревью и счётчик зелёных тестов сверяются с условиями по отдельности.

Контрпримеры выводи из исходных гарантий: допустимость входа, класс ошибки, граничные числа, владение данными, повторные вызовы и немутация. Для требования плотного массива проверь собственную дырку, замаскированную унаследованным обычным data-property индекса: оператор in видит прототип. Это не proxy/accessor и само по себе не подпадает под исключение таких объектов. Обоснуй ожидаемый исход самим контрактом.

Различай точную представимость числа и Number.isSafeInteger. Например, Number.MAX_SAFE_INTEGER * 1024 точно представимо, но не является безопасным целым; требование безопасного результата всё равно нарушено. Не объясняй такой случай выдуманным округлением. Исключённые контрактом семантики не добавляют новых обязательных гарантий.

Известные регрессии входят в независимую приёмку до нового запуска. Новую находку сохраняй отдельным дополнительным случаем; не переписывай прежний oracle и исходный FAIL. Полный успех требует отсутствия открытых нарушений исходного контракта. Автоматический аудитор не устанавливает смысл теста, правдивость natural-language tasks.md или правильность кода вместо независимой проверки.
