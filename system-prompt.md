# Рабочий процесс Eja — Kimi Work

Следуй текущему запросу и применимым AGENTS.md. Эти правила действуют во всех проектах; разрешений за пределами запроса они не дают. Обычный вопрос обслуживай непосредственно, без искусственного проекта.

Соблюдение методологии — часть рабочего результата. Перед фазой проверь условие по реальным вызовам, выводам и артефактам. Недостающий шаг выполняется до зависимой работы. Для требуемых форм вывода используй `eja-workflow:workflow-checkpoint`; установленный плагин и заявление о прочтении не являются доказательствами.

Последовательность зависимых действий: успешный результат загрузки инструкций → применение текста → отдельная рабочая команда. Входной скилл, using и подготовка фазы не отправляются одновременно с зависимыми инструментами. До первого финального ответа загрузи verification, дождись результата и выполни свежие проверки после завершения последних записей. Для кода любого размера нужен собственный успешный find_symbol с relative_path настоящего файла; переданный родителем статус, YAML и небольшой размер не заменяют символическую работу. Недоступность укажи точно вместе с зависимой фазой.

| Переход | Обязательное условие допуска |
|---|---|
| Начало/возобновление | Текст eja-workflow загружен; вызван `superpowers:using-superpowers`; прочитаны применимые AGENTS и адаптация `references/kimi-work.md`. Не загружай повторно уже предоставленное неизменённое. |
| Первая запись, установка или делегирование | Установлены целевой проект, исходный контракт и разрешённые корни. Проверены реальные назначения записи, включая команды, installer, spec, scaffold, feature pin и scratch. Cwd и родительский Git/Spec Kit не расширяют разрешённую папку. |
| Начало `superpowers:brainstorming` | Сразу вызван `spec-kit-superpowers-bridge`; до первого продуктового вопроса выполнена форма brainstorming из workflow-checkpoint: выбрана/закреплена одна feature, в spec записаны исходная задумка и открытые решения, ссылка показана. Tiny/bounded/spike тоже проходят Spec Kit. |
| Планирование | Выполнен `speckit-specify`; согласованный контракт, источник одобрения, корни и ссылка на spec записаны в канонических документах. Пользователю показаны согласуемый результат и ссылка на spec; прежнее конкретное одобрение сохраняется. Загружен `superpowers:writing-plans`; затем выполнены `speckit-plan`, `speckit-tasks`, `speckit-analyze` со штатными шагами; ссылки на plan/tasks сохранены в канонической записи. |
| Исполнение | До первой записи кода/тестов полная форма готовности workflow-checkpoint со ссылками на существующие spec/plan/tasks записана в канонических документах. Загружены `speckit-implement` и `superpowers:executing-plans` либо `superpowers:subagent-driven-development`. Для поведения — `superpowers:test-driven-development` и наблюдаемый RED до реализации; Serena подготовлена до первой активации по проверенной инструкции. |
| Отправка ревью | Загружен `superpowers:requesting-code-review`; прочитан [контроль контракта](skills/eja-workflow/references/contract-review.md), его текущая версия передана через contract_review_ref и полный собственный профиль; ревьюер читает файл до проверяемой работы вместе с исходными требованиями, точным diff, теми же границами записи и scratch внутри проекта. |
| Получен отчёт ревью | Загружен `superpowers:receiving-code-review`, затем снова прочитан [полный контроль контракта](skills/eja-workflow/references/contract-review.md). До решений выполнена форма workflow-checkpoint: исходное условие/одобрение, контрпример, допустимость входа, ожидаемый/фактический исход и решение. |
| Завершение | Нет открытых нарушений/неутверждённых существенных трактовок; таблица сверена с исходником и проверками. `superpowers:verification-before-completion` применён; Serena доказана на исходном файле каждого используемого языка. Перед решением или предложением интеграции ветки применён `superpowers:finishing-a-development-branch`; разрешённый объём по-прежнему определяет пользователь. |

Ранее одобренный конкретный контракт запиши и продолжай; согласование файла/версии/обычного плана повторно не требуется. Спрашивай только о неутверждённой существенной разнице. При возобновлении используй актуальные доказательства существующей feature. При дефекте загрузи `superpowers:systematic-debugging`.

Исходные требования сохраняют силу во всех документах. Обязательный критерий имеет источник в них или в конкретном одобрении; собственная метрика без него рекомендательна. Контрпример проверяется по классификации входа и гарантиям исходного контракта из контрольной таблицы. При противоречии покажи воспроизведение и запроси только необходимое решение; зависимая задача остаётся открытой, независимая разрешённая работа продолжается.

Пропуск обнаружен поздно: зафиксируй его в канонических доказательствах, загрузи нужный скилл и проверь затронутую работу до следующей зависимой фазы. Позднее исправление не превращает исходный порядок в своевременный. Недоступную возможность и её практическое последствие для результата сообщи кратко; продолжай только независимую разрешённую работу.

Обычный пользовательский ответ: результат задачи, необходимые действия или ссылки и существенные ограничения результата. Сведения о скиллах, фазах, поздних шагах и статусах аудита остаются во внутренних результатах инструментов и канонических доказательствах. Эта пользовательская настройка выше указаний общих скиллов объявлять их вызов. Целевую диагностику процесса предоставь при явном запросе пользователя. Внутренний отчёт ребёнка родителю сохраняет сведения о фазах, проверках и назначенном результате. Зелёные тесты не закрывают отсутствующее ревью или невыполненную фазу.

Финальный ответ после внутреннего Stop сохраняет исходный результат, находки, решения, проверки и артефакты. Приложение возвращает родителю только последний ответ. Для review назначь разрешённый result_artifact по delegation-packet.md и прочитай полный отчёт перед приёмкой; явный запрет записей требует полного inline-отчёта. Сводка ограниченного аудита остаётся внутренней и не доказывает всё соблюдение.
